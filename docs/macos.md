# Draggy for macOS

The macOS app is a SwiftUI shell over the shared Rust core. It lives in `macos/`, needs macOS 14 or newer, and builds for Apple silicon only. It does not touch `win/` or `linux/`.

## How the core gets in

`macos/scripts/build-core.sh` builds `draggy-core` as a static library for `aarch64-apple-darwin`, runs `uniffi-bindgen` to generate the Swift bindings, and packs the library and header into `DraggyCoreFFI.xcframework`. The local Swift package `macos/Packages/DraggyCore` wraps that framework and the generated `draggy_core.swift`. Both are build output and are gitignored.

`macos/project.yml` describes the Xcode project. The project file itself is generated by XcodeGen and not committed.

## Build and test

You need a Mac with Xcode 16 or newer, Rust, and XcodeGen (`brew install xcodegen`). From the repository root:

```bash
macos/scripts/build-core.sh
cd macos
xcodegen generate
xcodebuild test -project Draggy.xcodeproj -scheme Draggy -destination "platform=macOS,arch=arm64" CODE_SIGNING_ALLOWED=NO
```

CI runs the same steps on `macos-15` (`.github/workflows/macos.yml`).

## What is in it

- Settings: server address, model name, and an API key kept in the Keychain as a generic password under `com.draggy.app`. An empty value deletes the key.
- Chat: type a message and watch the reply stream in. A turn goes through `draggy_core.Session`, and the core's events arrive on a `TurnObserver`. The transcript logic is a plain value type (`Transcript.swift`) with unit tests.
- Tests for the Keychain store and the transcript.

## What is missing

- The transcript view is a placeholder. It is a SwiftUI `LazyVStack`. The plan calls for an `NSTableView` with TextKit 2, and this view has to be replaced before any streaming performance is measured.
- No tools. Turns run with commands disallowed and no approval sheet, so the core's approval questions are never answered.
- No saved conversations, markdown, or attachments.
- No engine or model management, documents, or web panes.
- No signing, notarization, Sparkle updates, or release workflow.

## Not verified

No Swift in this directory has been compiled. The author's machine runs Windows. The first macOS CI run is the first real check, and these are the places most likely to break:

- the names and `Sendable` conformances in the generated UniFFI bindings, which `AppModel.swift` assumes
- Swift 6 strict concurrency against the generated code
- Keychain access on a CI runner
- XcodeGen picking up `shared/icons/icon.icns` as a resource
